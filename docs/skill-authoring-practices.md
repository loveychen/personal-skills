# Skills 写作技巧：让规则改变行为

用于维护本仓库，不属于论文阅读时必须加载的指令。依据规范与官方指南整理，具体访问范围见[来源记录](../skills/paper-deep-reading/references/sources.md)。

## 先写可观察的任务合同

明确输入、触发、产出、边界和失败时的可行退路。描述首句前置最主要的任务与关键词，避免把整个工作流塞进元数据，或靠“适用于所有研究”吸引无关请求。

例：`Use when closely reading a named LLM or AI agent paper...` 能定位具体论文共读；独立找论文、全文翻译、正式审稿、技能创建分别有不同目标，不应都挤进同一个技能。

描述可以简述能力，但不能替代正文。保留既有技能名和调用方式能减少迁移成本；只有明确需要才修改默认调用策略。

## 写决策，不写仪式

把笼统质量要求变成改变下一步的规则：

| 泛泛指令 | 可执行写法 |
|---|---|
| 深入分析实验 | 新模型、多样本和 verifier 同时改变时，区分系统收益与单一训练目标的贡献 |
| 保持批判性 | 每项实质质疑连接原文观察、受影响结论、替代解释和能区分的检查 |
| 因材施教 | 读者只懂聊天模型时先解释一次工具调用，不同轮展开全部模块 |
| 旁征博引 | 先确定一个外部疑问，查最近原始来源，解释关系后返回主线 |

固定步骤仅用于确实容易失真的环节。不要强制每轮问问题、读取所有参考、生成所有表格、凑文献或批评数量。与用户明确要求冲突时，保持任务目标并遵从用户选择。

## 渐进披露与结构

`SKILL.md` 保留目标、默认行为、关键边界与参考路由；复杂专用分支放 `references/`，直接写明何时读。尽量让正文直接链接到需要的文件，避免多级跳转。500 行/约 5000 tokens 是规范与指南中的建议上限，不是追求目标。

本次路由：LLM 读机制/预算指南；Agent 读交互/环境指南；写评论时读批判性写作；保存时读状态规则。域检查表留作选择，不印在每次回答里。

相同原则只维护一处，其余文件补专用决策。例子要短、具体且标明合成/真实，展示期望推理与证据边界；不要把原始评测答案直接复制成唯一教学例子，再把同题成功当泛化证据。

## 证据与版本

区分格式规范、厂商/研究者经验、原始实验与设计综合。引文说明采用了什么、实际读到哪里、什么不能推。技能自己的行为测试不能替代其领域方法的科学验证。

对 LLM/Agent 这类变化快的主题，保留来源版本与核验日期，避免把榜单、API 行为或某次研究比例写成永久事实。用户进度、论文和访问凭据不进入全局技能包。

## 用真实行为验证

先保存当前版本或无技能的基线，观察实际行为；没有失败就如实记录，不能为证明改进而制造失败结论。再用真实任务验证新规则是否能指导有用的回答。

至少区分四层：

1. **结构**：YAML、命名、路径、引用和 UI 元数据可用。
2. **触发**：显式/隐式/上下文请求能发现，相邻但不同的请求不误触发。
3. **行为**：实际轨迹是否取到原文、遵从要求、处理不确定性并交付结果；不能只匹配标题或关键词。
4. **效果**：是否帮助真实读者解释、迁移和保留知识，需要另行观察；不由一次输出流畅推出。

条件允许时做多个独立运行，给执行者原始任务而非标准答案，人工检查所有关键失败。重测应由修改、失败或未解风险驱动；不要反复跑相同检查只增加“通过次数”。单次冒烟、开发例、保留例和真实论文定点检查分别标记。

## 本次取舍

`paper-deep-reading` 保留一个入口，新增 LLM、Agent 和批判性写作三份运行参考，而不是另开多个互相争抢触发的技能。技能编写技巧保存在本指南；没有新增模型/API 依赖或可执行脚本。
