# 技能设计

把重复任务整理成最小、可验证的技能设计。先继承用户和仓库已有信息，不发背景问卷；明确要求“只设计”时只交付设计，不创建业务技能文件。

## 工作方式

1. 定位现有技能与相关指南，判断应新增、扩展还是只改文档；有相近入口时说明实质差异，避免抢同一触发。
2. 用已知需求确定实际使用者、材料、产出和最关键的失败边界。缺信息确实影响设计时只问关键问题；其余给出可修正的假设。
3. 先设计一条代表任务和一个相邻但不该触发的请求，再确定最少参考文件。只在确定性重复操作值得自动化时建议脚本。
4. 提出会改变助手下一步的规则：条件是什么、应采取什么动作、得到什么可检查结果。把口号、固定提问数和强制凑输出数量改为任务相关决策。
5. 定义验证重点：正确触发、正常任务、缺材料或用户改变偏好。区分开发例与独立检查，不能把技能内示例当陌生任务验证。

## 设计交付

用简短设计给出：**目标与范围、中文描述、输入与产出、关键决策、文件安排、代表场景与验证方式**。已有文档直接引用，不重抄；小改动仅解释受影响部分。

技能名称和调用标识符使用稳定英文形式，描述及面向读者的文案使用中文。保留用户控制节奏与范围的能力，不让技能自动扩大外部操作授权。

需要写法实例时，按需读 [技能写作技巧](../../../docs/skill-authoring-practices.md) 的相关部分；落地目录与提交方式见 [新增与维护技能](../../../docs/adding-skills.md)。引用路径均相对本文件，不能从调用时的工作目录猜测。
