# 怎样完成一轮有用的辩论

本参考用于角色较多、分歧复杂或需要多轮修订的方案。主助手只保留会影响决定的内容，不要求每位参与者提交完整报告。论证和检验方法见[严谨论证与共识方法](rigorous-consensus.md)。

## 主持人怎样连接前后两轮

一轮讨论用于推进具体问题，不代表整个任务已经完成。主持人应向本轮相关角色提供当前方案、前轮仍有效的结论、新证据和需要解决的问题，并说明该问题与最终目标的关系。首轮分别形成判断，后续轮次针对需要更新的部分深入，不要求每人重复完整报告。

每轮结束时，主持人应简要说明：哪些主张得到支持或被撤回，方案发生什么变化，哪些异议或假设仍阻止决定，以及下一轮准备怎样消除障碍。下一轮可以换一种提问方式、安排共同查证、要求比较替代机制或检验关键反例，不能只延长相同争论。

各方暂时一致也不自动代表目标已达到；主持人应检查其共同前提、必要证据和实际方案是否仍有遗漏。旧结论可以因新证据被推翻，主持人应记录理由。完成条件已经满足时，主持人应组织最终确认，不设置固定最低轮数；确实超出权限或用户要求停止时，主持人应如实保留未完成状态。

## 先形成各自判断

主助手应固定目标、约束、方案版本、共同材料和完成判据。复杂争议默认覆盖五种视角，并补齐真正受影响方；视角与代理数量可以不同，主助手应保留初始判断的实际来源，不把同一资料的重复引用说成独立证据。

每个角色应说明支持什么、要保护什么、依据和推理是什么、最低可接受条件是什么，以及哪些偏好可以调整。角色还应说明什么证据会改变判断。角色认为某项条件不可退让时，应解释它来自事实、有效要求还是效果预测。

## 针对具体主张质询和回应

| 内容 | 应记录什么 |
| --- | --- |
| 关键主张 | 哪个角色在什么条件下支持什么选择 |
| 依据与推理 | 证据是什么，为什么能够支持这项主张，还有什么隐含前提 |
| 质询 | 对方认为哪项前提、推理、代价或边界有问题 |
| 回应与检查 | 被质询者接受、反驳或收窄了什么；哪份原件或检查可以区分解释，实际结果是什么 |
| 方案变化 | 主助手修改了哪些动作或条件；保留原方案时说明理由 |
| 剩余障碍 | 哪个具体问题仍阻止角色接受，需要什么变化才能消除 |

事实问题需要查证，机制和效果主张需要相应检查，真实价值取舍需要有权决定者选择。被质询者应回答异议本身，不能只重复立场。角色可以有据改变观点；没有实质分歧时，主助手应检查共同依据和未知，不必制造争吵。

## 把意见变成共同方案

主助手应寻找能满足关键利益的方案，不能一直只问甲乙哪个赢。主助手应将成立的修订落实到正文，并让相关角色判断修改是否消除了原异议。没有必要修改时，主助手可以保留原方案，但应说明理由。

每项重要检查都应有机会发现错误。主助手应检查关键反例和相邻行为，不能用预设正确输出、角色自评或一次成功证明净收益。没有进展时，主助手应改变问题或方法，而不是自动结束或增加轮次。

## 在同一版本上总结和确认

主助手应请所有需要参与共识的角色分别作最后回应：是否接受这个具体版本，理由是什么，自己调整了什么偏好，还承受哪些代价和证据限制。附条件接受时，主助手应核对条件是否已经成为可执行条款。

共同约束不等于共同方案，接受试验不等于接受采用。一方仍有实质异议时，主助手应继续处理该异议；真实障碍超出权限时，主助手应报告未完成及最小需要补充的决定。最终交付必须同时满足入口中的论证、共识和产物要求。

## 示例：资料检索方案

以下是虚构讨论示意，没有发生实际模型或服务运行，也没有形成真实参与者共识。

当前候选使用每日快照回答所有服务状态。实践者关注实施速度；学者要求区分快照与实时状态；怀疑者提出反例：用户问“现在是否恢复”，昨日快照不能回答；经济学家关注实时查询的资源支出；历史学家检查过去是否因陈旧资料误报恢复。

如果接口原件仅支持带时间戳的快照，主助手应撤回“能回答当前状态”的主张。主助手可以提出共同候选：历史问题使用快照并注明时间；当前状态只有在存在获准实时来源时才查询，来源缺失时明确当前状态未知。

这个候选仍须符合目标。用户要求必须取得实时状态时，未知答复不满足目标，主持人不能把诚实说明限制当成已经解决。用户允许在当前资料边界内给出可信答复时，各方可以检查陈旧快照、实时入口缺失和历史查询三个情形，再决定是否接受该规则。角色分别确认同一版且必要检查通过后，主助手才可以将该设计任务报告为完成。

## 示例：新原件到来后，主持人怎样更新判断

以下也是合成方法示意，不是独立角色对话或真实接口验证。目标是纯库存查询不得创建订单或改变可售库存。首轮角色因为工具名为 simulate_quote、参数为 dry_run，且演示返回HTTP 200，倾向复用该入口；此时没有接口副作用说明。

主持人首先把“接口是否只读”列为待查前提，不能由名称和成功状态推出安全。下一轮收到接口说明：dry_run只表示不生成正式订单，仍会创建临时预留并减少可售库存；另有read_stock声明effects为空，并返回观测时间。主持人据此将前一入口从“依据不足”更新为“违反当前目标”，而不是把自己首轮保留未知写成首轮已经判断错误。

主持人应回应具体异议：实践者说“不生成正式订单”，只覆盖了目标的一半，仍需回答库存为何被改变。修订后的候选可以使用有只读依据的查询入口，答复注明观测时间，失败时不得回退到会预留库存的工具。接口说明支持这项设计选择，不证明真实部署已经无副作用。

主持人应把同一版修订和新原件交给相关角色继续判断。其他角色尚未回应时，主持人不能替他们接受，也不能把“已改正文”当成最终共识。此例展示原件如何改变问题与方案，不要求每个任务固定两轮或使用这些工具名称。
