# 方法来源与适用边界

本文用于追溯出处、说明实际阅读范围和延伸阅读，不是运行本技能的前置步骤。执行所需的方法已经整理在[本地方法摘要](rigorous-consensus.md)及其他包内参考中；主持人正常使用本方法时，不需要逐一访问下面的链接。

用户要求阅读原文、来源解释存在争议，或当前任务需要核对原始论述时，主持人可以按任务及宿主规则查阅对应来源。这不限制处理实际问题所需的事实检索；本地摘要不足或过时时，主持人仍应说明缺口并按授权补充。

本技能将用户提供的多角色讨论材料、公开工作中的可迁移思路与方案迭代实践组合使用，并非任何单一来源发布的统一流程，也未证明通用最优。

## 用户提供的材料、引用与参与者视角

用户提供的[知乎原帖](https://www.zhihu.com/pin/2097276002762233406)正文明确提到两条来源：[Rahul 的学习方法文章](https://x.com/sairahul1/status/2068250224532050089)与下文列出的 STORM 论文。主代理已通过正常浏览器读取 Rahul 原文，并对照论文确认引用对象。两者分别讨论学习反馈过程与多视角研究，不能混成同一个未经区分的来源。

该帖还包含两张相关图片：第一张方法图列出实践者、学者、怀疑者、经济学家和历史学家五类参与者；下一张以“矛盾图谱”呈现不同判断的冲突、证据强弱、关键问题、共识与盲区。

本技能借鉴的是这些参与者的不同关注点：实际可行性、研究依据、反例、成本与激励，以及历史条件。复杂争议默认覆盖这五种视角，并根据问题说明不适用的视角及真正受影响方；这项默认是本技能的设计选择，不是论文的固定要求，也不构成每次必须启动的五人编制。参与者应分别提出判断，针对具体分歧相互质询并回应，主助手再将成立的意见落实为方案修订；证据查证与相应验证约束这一过程。

原图将第一步称为“五视角 STORM”。本次讨论中，用户要求关注的是图中参与者的角色设定与研究视角；本技能不将这份五角色清单表述为斯坦福 STORM 论文规定的角色体系，也不以原图的称呼证明两套方法完全相同。

作者提供学习阶梯、限时学习计划、逐题测试、一页摘要、筛选资源和复述纠错六类提示词，并将学习组织为路径、测试、压缩及反馈重复。本技能可以参考目标分解、主动检验和反馈修订的思路，但不要求固定20小时、固定资源数量或反复考问用户。原文没有提供“10倍速”的对照实验，标题不能当作效果证据。

### 2. STORM：多视角提问与资料综合

- 论文题名：Assisting in Writing Wikipedia-like Articles From Scratch with Large Language Models。
- 作者及发表：Yijia Shao等，NAACL 2024，页码6252—6278。
- DOI：`10.18653/v1/2024.naacl-long.347`。
- [正式发表页与引用信息](https://aclanthology.org/2024.naacl-long.347/)；[正式PDF原文](https://aclanthology.org/2024.naacl-long.347.pdf)。

- [官方代码与项目说明](https://github.com/stanford-oval/storm)。

这是知乎正文点名引用的研究来源。系统从相关主题发现视角，模拟不同视角下的提问及基于检索资料的回答，再综合信息形成提纲和文章。本技能可以参考问题发现、检索与综合方法，但论文的文章组织和覆盖实验不能证明工程方案准确率。上述图片中的固定五角色表及“矛盾图谱”仍以图片为直接来源，不归为论文规定的固定配置。

## 对方案设计的综合借鉴

以下是本技能对两条来源及配图的迁移解释，不是原作者直接给出的工程设计标准。

| 可以借鉴的观点 | 迁移到方案设计时，可以怎样使用 | 应保留的边界 |
| --- | --- | --- |
| 学习应围绕可完成的目标组织 | 助手先确定结果使用者、真实任务、必要能力和完成条件，再安排研究顺序 | 助手不能把固定学习时长或资源数量变成所有任务的要求 |
| 不同参与者会发现不同问题 | 助手选择适用视角，分别提出实际可行性、研究依据、反例、成本激励和历史条件问题 | 视角不等于固定代理数量；角色名称与意见数量都不是事实证据 |
| 角色之间需要针对分歧回应 | 参与者指出对方具体主张及证据缺口，被质询者接受、反驳或收窄主张；主助手说明方案如何改变 | 角色不必预设对立，也不能把单助手角色分析说成独立专家共识 |
| 新答案可能暴露新的缺口 | 助手依据资料继续追问影响选择的前提，区分事实冲突、条件差异、价值取舍和未知 | 助手不能为延续讨论而重复追问，也不能以共识替代查证 |
| 理解需要通过实际任务检验 | 助手先明确目标行为与判据，再按授权用代表情形及相邻反例检查候选 | 解释、预设输出、模型自评与真实执行分别支持不同结论；学习提示词不构成工程效果证明 |
| 有效认识需要压缩并接受反馈 | 助手保留简明结论、适用条件、关键证据和未决项；具体错误出现后，助手修改受影响部分并进行相应检查 | 摘要不能替代执行必需的完整规则，材料变短也不能单独证明质量提高 |

这组借鉴用于帮助助手发现问题、组织证据和修订方案，不能直接推出某一种架构必然最优。简单任务仍可直接处理；涉及部署、发消息、采购或模型／业务调用时，助手仍须遵守任务授权。

## 论证、检验与协商的专业依据

本技能还参考 van Eemeren 与 Grootendorst 的批判性讨论理论、Browne 与 Keeley 的《Asking the Right Questions》（《学会提问》）、Mayo 的严峻检验思想，以及 Fisher、Ury 与 Patton 的原则谈判方法。它们分别帮助主助手组织论证责任、发现值得追问的缺口、选择能够发现错误的检查，以及从各方利益构造共同方案。具体操作与迁移限制见[本地方法摘要](rigorous-consensus.md)；出版社原文入口和实际阅读范围见下节。这些理论不能被当成本技能已经有效的证据，也不与 STORM 论文或配图混为同一来源。
