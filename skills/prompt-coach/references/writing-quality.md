# 指令写作：逻辑结构、专业性与可读性

用于诊断和改写指令中的具体表达问题，不用于给用户评分。以下为原创模拟示例，不是专家原话。方法与本包的任务表达、具体反馈原则一致；目标是准确易读且保持指令行为，不能据文字更顺就宣称执行收益已验证。

## 1. 结构服务于关系，不是统一排版

检查：目标与背景是否混成命令，条件究竟约束哪个动作，并列项是否处于同一层级，先后次序是否反映真实依赖，输出要求是否容易找到。只有这些关系需要澄清时才分段或列项。

模拟原句：

> 检查两份结果是否可比，配置和数据范围一致才比较指标，否则只说明差异；全程不要补跑，两种情况下结论都要列出已知限制。

等价整理：

```text
先检查两份结果的配置和数据范围是否一致。
- 两者都一致：比较指标。
- 任一不一致：只说明差异。
全程不补跑。
无论是否可比，结论都列出已知限制。
```

理由应讲清：把可比与不可比两条分支放在同一层，读者不用回读来判断“否则”对应什么；把共同输出单列，避免误读为只在不可比时报告限制。没有新增验证步骤、许可或结论。短而清楚的原句也可保留，这不是所有任务都必须采用的模板。

## 2. 专业性来自准确，不靠堆叠名词

模拟原句：

> 对检索链路开展耗时归因能力建设，通过 trace_id 做日志对齐，分别看检索和重排的 p95 延迟；先提供分析，不改线上配置。

上下文已经明确：“能力建设”在此仅指用已有日志分析耗时，不是开发新监控系统。

等价改写：

```text
用 trace_id 关联检索链路的现有日志，分别分析检索和重排阶段的 p95 延迟。
本轮只提供耗时分析，不修改线上配置。
```

理由应讲清：将已被上下文解释清楚的抽象说法换成“关联日志、分析延迟”两项动作，保留 trace_id 与 p95，因为它们有精确技术含义。若上下文未解释“能力建设”，不能擅自删掉可能包含的开发任务；应指出歧义，而不是替用户定案。

## 3. 拆句时核对条件、范围与要求强度

“仅当A且B才做C，否则做D”不能变成“A或B时做C”；“可以重试”不能变成“必须重试”；“分析后经确认才能发布”不能变成“分析并发布”。

重排后核对的是允许行为，不只是关键词是否仍在。例如全局约束移到某个分支下面，可能会错误缩小其适用范围。必要限定、否定和例外要跟随它们所限制的动作一起移动。

## 4. 对三类写作问题给不同反馈

- **表达本来清楚且符合文体偏好：** 可以原样保留；用户明确希望纠正口语化时，可在保留含义的前提下规范表达，说明这是表达校正，不是信息缺项，不为展示工作量制造缺陷。
- **含义确定但难读：** 调整段落、句式或用词，指出具体关系如何更容易识别，不声称原任务曾执行错误。
- **原意不确定或冲突：** 把问题单独指出，不在改写中悄悄选择解释，也不为了填满“目标—步骤—验收”而补造要求。

复盘自己的理由也遵守这些写作要求：先给具体判断，再给依据和解释，必要限制靠近对应结论。避免用含糊的专业词解释另一个含糊专业词。

## 5. 纠正口语习惯：先识别概念，再采用通行表达

当用户明确希望纠正口语化时，目标不是保留原口吻或仅换成客套公文。用“原说法—对应概念—建议表达—含义与边界”教会用户更准确地表达；形式按需要简化，不要求每次输出四列表格。概念来自原意和上下文，不能为了换一个术语替用户新增目标或选定方案。

以下均为自拟模拟例子；来源支持术语含义，不证明例子中的系统已经实现相应性质。2026-10-27核验：

### 回归测试：修改有没有影响原有功能

原说法：“改完以后看看，别把原来能用的地方弄坏，只检查，不改代码。”

建议表达：“对本次修改影响的既有功能进行回归测试，检查是否引入回归。本轮只检查，不修改代码。”

解释：回归测试关注修改是否在软件原有部分引入或暴露缺陷；它不等于只重跑此前失败的那一条测试，也不意味着无条件运行所有测试。来源：[ISTQB术语表v3.3发布说明，p.11](https://api.glossary.istqb.org/storage/help/R0uz58NqLzUz48LVUuyGSF76NFj4LHQazSs0GlNS.pdf)。该旧版来源用于核对这里的概念示例，不当作最新完整术语表。

### 幂等性：同一请求重复执行，不重复产生业务结果

上下文已明确讨论同一业务请求。原说法：“同一个提交请求发两遍，别多生成一条记录；先检查，别改实现。”

建议表达：“检查该操作的幂等性：对同一业务请求重复调用时，不应重复创建业务记录。本轮只检查，不修改实现。”

解释：这里关心的是重复操作的预期效果，不是请求只执行一次，也不是返回文本必须完全相同。不同业务请求不能仅因为内容相似就合并。来源：[RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)定义HTTP方法的幂等语义；本例借此解释重复请求效果，具体业务实现仍需核查，不能只看方法名就宣称成立。

### 无法直接选术语：口语表达可能隐含不同机制

原说法：“给这个流程加个兜底。”如果上下文没有说明期望的失败处理行为，就不能直接改成“实现幂等重试”或“增加回滚”，因为这些词已经替用户选择了机制。

可先写成“为该流程补充失败处理机制”，同时在成稿外指出仍需明确失败时的预期行为；这只是规范了说法，没有消除原意的缺项。已知是再次尝试、保留部分功能或恢复之前版本时，才选择相应术语并核对其领域定义。

专业表达要让目标读者理解。首次引入陌生但必要的术语时给一句释义或小例子；普通动词已经准确时直接使用，不将“整理结论”包装成自创的“认知资产治理”等概念。
