在协作中练习提问与判断

交付后可以复盘指令并获得可复制的下一步请求。普通对话中也可以开启思考提示，练习检查假设、证据和结论。

适合希望边工作边改进任务表达的人。先完成工作，再给反馈；既不替代主任务，也不要求每条指令写成长篇模板。

安装与验证

先从维护者提供的可信地址取得包含本技能的仓库，并在终端进入仓库根目录。需要 Node.js、npm/npx 和包管理网络；安装前检查目标助手及是否已有同名技能。项目级与用户级安装范围不同，请按实际需求选择。

# 在已取得的仓库根目录，先查看可安装技能
npx skills add . --list
# 只安装本技能到所选助手的用户级目录，按提示选择助手
npx skills add . --skill prompt-coach --global

如使用项目级安装，在目标项目目录执行 npx skills add <仓库路径> --skill prompt-coach。仓库地址和版本由分发者提供；若使用浮动分支，安装结果可能随版本变化。选择复制时，之后的更新需要重新安装；选择链接时，源目录移动或删除会使链接失效。

也可手动将完整的 skills/prompt-coach 目录复制到助手支持的技能目录，保留 SKILL.md、references/ 和许可证。已有同名技能时先比较并备份，避免覆盖不同版本。以下是常见用户级入口，实际路径可能受版本、配置或运行环境影响：

  • Codex：~/.agents/skills/prompt-coach。
  • DSH：~/.agents/skills/prompt-coach 或 ~/.dsh/skills/prompt-coach；需启用文件系统技能提供器和 skill 工具。
  • Claude Code：~/.claude/skills/prompt-coach。
  • Pi coding agent：~/.pi/agent/skills/prompt-coach 或 ~/.agents/skills/prompt-coach。

参考官方说明：Skills CLI、DSH、Claude Code、Pi。不同宿主对路径和调用命令的支持可能变化，以实际版本为准。

安装后分步检查

  1. 开始一个新会话，查看助手的技能列表或让它报告是否发现 prompt-coach；管理器列出名称不等于助手已加载。
  2. 明确要求“使用 prompt-coach 复盘一个模拟任务”，核查工具记录或助手可见的加载信息，确认正文及参考资料可访问；Claude Code 可用 /prompt-coach，Pi 可用 /skill:prompt-coach，其他宿主按其界面调用。
  3. 在新会话提交一个不提 Skill 名称的普通任务；检查先交付结果、再给复盘和两个可复制请求。另测“只给结果”是否跳过附录。记录宿主版本、模型、输入和实际结果；如需要，再配置下方的可选约定并分别验证。

找不到时检查安装范围、同名覆盖、完整目录和宿主的技能功能是否开启；能显式调用但未自动追加时，检查目录和模型选择、是否实际加载技能、可选常驻指令是否生效及是否有更具体的例外。单次成功不证明每轮稳定触发或反馈质量达标。

如何开始

需要支持 Agent Skills 的助手，以及本次请求、关键约束和交付结果。材料已经在同一对话中时，可以直接引用，不必重新整理全部记录。这个技能没有必需的模型 API、脚本或内部服务依赖。

使用 prompt-coach，在完成当前任务、给出结果后，
对照原话和实际结果，检查逻辑结构、术语与可读性，
给出最小必要的改写或保留示例，
解释这处表达如何影响执行选择，而不只评价“更明确”。
再给两个基于实际结果的下一步请求，用独立代码块展示完整正文，
说明为什么值得做、会推进什么判断，以及适用条件。
默认行为与可选约定：本技能设计为任务交付后提供复盘，但宿主可能不会自动加载。希望进一步明确这一偏好时，可自行在助手支持的用户级指令或项目约定中追加下面的规则；先检查现有文件，勿覆盖已有配置。Codex 常用 ~/.codex/AGENTS.md，DSH 常用 ~/.dsh/AGENTS.md（自定义 home 或 profile 可能不同）；Claude Code 和 Pi 请按各自官方文档配置。
完成当前有效任务并交付结果后，使用 prompt-coach：
对照原指令、当时上下文和实际结果，给出一个可复制的改写或保留示例及具体理由；
再给两个基于结果、各自完整可复制的下一步请求，并说明价值和限制。
只给结果、严格格式或关闭附录时遵循用户要求；只关闭一部分时保留另一部分。
进度、纯确认、状态询问和未完成任务不强加附录，不自动执行建议。

安装 Skill 本身不会修改常驻规则，也不保证每轮触发；用户可按个人偏好补充术语和表达要求。

只想看结果时说“这次只给结果，不要附录”；也可以只关闭复盘或只关闭下一步建议。对于已经结束的任务，明确指定要分析的请求及结果。

工作流程

日常对话中的思考提示

可以直接说「请用 prompt-coach 在这个聊天里给我思考提示」。如果希望新会话也使用，可以在宿主支持的用户级指令中加入这项偏好。新会话可用一条包含具体推断的普通消息检查是否触发，再用「只给结果」检查是否能跳过。

例如，你说「换到窗边后写得更顺，以后一直坐窗边就好」。助手可以问「那天也没开会，如果还是在原座位，你会预期同样专注吗？」然后点明这是在找替代原因。若还值得考虑结论是否适用于其他工作，可以同一轮指出。

也可以说「用一个具体例子，只改一个条件，让我先预测」。助手等你回答后再对照证据、点明模式。可以留意之后遇到另一个话题时，你会不会自己想到同样的问法。查看思考提示与练习规则

一个示例，两三条具体理由

从原话和产物中指出哪处表达影响了执行，解释改写与原话的实际差别、取舍和适用条件。已有要求被忽略时，明确归为执行偏差；原指令充分且符合文体偏好时可保留。

前瞻 · 能直接使用

两个完整下一步请求

必要背景、资料入口、行动、范围和预期产出都在各自代码块内。标题可以短，正文不藏在按钮里；推荐理由在正文外。

反馈会区分指令缺项、代理执行偏差、环境限制与证据不足；来源只支持相应方法，不替当前任务证明原因、排序或收益。公开原例和根据方法生成的示例会分别标注。

指令也要有好的写作结构

复盘不仅看要求是否齐全，也看读者能否顺着文字准确理解它。下面三项按实际问题检查，不要求每次填表或给分。

  • 逻辑结构：目标、背景、行动、约束和交付关系清楚；同层信息分组，条件靠近对应动作，先后和例外不被重排改变。
  • 专业性：术语准确、概念一致，保留必要技术标识；用具体对象和动作替代无信息的黑话，保持文体所需的正式程度。
  • 可读性：主体和指代明确，句段按意思组织，长句可拆但不丢限定；短而清楚且符合文体偏好的请求可以原样保留。

希望纠正口语化习惯时，可以明确告诉助手。它会指出原说法对应的概念，建议领域通行、定义适用的术语，并用短解释或例子帮助理解；不会以保留原口吻为由跳过校正。没有合适术语时，用准确的普通工作表达，不生造听起来专业的名称。原意、逻辑结构和可读性仍优先。

例如，修改后“看看以前能用的功能有没有被弄坏”可用“回归测试”说明检查目的；同一申请重复提交不应多建工单，可用“幂等性”说明预期效果，并附一句释义。“加个兜底”则不能直接等同于某种重试或回滚机制，需要先明确失败后的期望行为。概念来源与适用边界见通行术语的使用示例。

纯写作调整保持行为不变。“且”不能变成“或”，“仅当”不能丢，建议不能升级为必须，分析不能变成已实施。字段、模板变量、路径和精确字符串不随文风改写；原文冲突另行说明。

例如，将“只有三项条件均一致才比较，否则列差异；所有情况都不补跑”拆成分支时，三项条件必须仍是共同前提，“不补跑”也必须仍覆盖两个分支。具体写法见指令写作检查与示例。

如果解释仍抽象，可以让助手用“原句—改写—为什么”逐项对照，必要时再给一个会改变含义的错误改法。多个例子应分别说明不同难点；模拟例子会明确标注。

一个具体示例

以下内容均为模拟，用来展示解释方式，不是专家原话或真实用户案例。

原请求：把上线说明改成一线客服能快速阅读的通知，150 字以内，保留生效时间、操作和求助渠道，只写不发送。

已交付：通知符合要求，没有遗漏或发送。

有用的回顾：原指令已充分，可原样保留。“150 字以内”允许压缩措辞，但三项必留信息限定了压缩的边界：不能为了变短而删掉异常求助渠道。只给字数限制时，助手可能把删掉关键信息也当作简化；同时说明读者要完成的动作，才把这个取舍交代清楚。以后需要短文案时可以复用这种写法；具体句序和同义表达仍交给助手。

如果你想演示另一种阅读方式，完整下一步请求可以这样写：

请把下面这份已完成的模拟上线通知改成一份客服快速问答，
用于读者只想查某一项信息的情况；只在回复中提供内容，不发送。

已有通知：新版客服工作台将于 11 月 1 日 09:00 启用。
客服当日上班前刷新页面，确认工单列表正常；异常时保留错误提示，
联系值班群。现有账号和权限不变，无需安装客户端。

仅依据这些事实，围绕启用时间、上班前操作、异常求助、账号权限
和安装要求组织简短问答。不得补写未知的群名、排障步骤或服务承诺。
交付完整问答，以五类信息均可定位、事实不变为完成依据。
这是新的可选用途，不需要重做已经达标的通知。

为什么值得这样问：连续阅读的通知已经完成。问答只在读者需要查单项信息时有额外价值；如果没有这种使用需求，就无需继续做。这说明的是用途和取舍，不是在制造原文缺陷。

通常输出会有两个不同方向；这里仅展示一条的完整程度。更多方法见教练理由示例和完整追问示例。

怎样判断反馈是否有用

先看它是否区分三种情况：确实缺少用户意图，才建议补最少的信息；原要求被忽略，应承认执行偏差；原指令充分，就解释有效取舍而不硬找问题。后来澄清的用途可以合并到下次请求，不能说成你一开始就已明确。

  • 能指出下次应保留或调整哪句话，并解释适用条件。
  • 结构、术语或句式的调整有具体作用，且没有改变条件、权限和要求强度。
  • 理由关联本次事实，不是换个任务也能原样使用的赞扬或口号。
  • 两个下一步请求推动不同判断，存在依赖时条件写在正文里。
  • 单独复制一个代码块，不需要再拼接原回复才能开始执行。
  • 不能确认的事实仍为未知；提出建议没有被表述成已经执行。

如果反馈没做到这些，可以直接指出实际障碍，例如“这条只给了方向，没有说明要交付什么”或“理由没有解释为什么现在应优先做”。无需为了得到改进而先写一份完整评测报告。

当前验证边界

核心规则沿用经过有限显式试用的版本，本仓库新增通用合成用例用于后续核对。既有试用检查过完整请求、具体理由、条件性选择和成功任务不强行找错；它不是严格同条件对照，也不证明长期学习收益。

结构检查只覆盖约定字段、链接、许可证及手册结构。新宿主的实际发现、每轮触发、全部用例行为与用户学习效果仍需在对应环境验证。没有当前任务证据时，Skill 不应编造历史或专家原话。

方法及适用边界见实践来源。教育反馈研究仅提供设计思路，不代表本技能效果已获该研究验证。

后续请求引用任务子目录资料时，助手应保留真实位置和所需规则入口；接收者无法访问时，可以内嵌必要片段。不得把候选假设或未提供的信息改写成组织事实。具体例子见完整追问的示例与反例。
