# Agent 论文：从一次行动读到系统证据

## 先看一次实际轨迹

Agent 名称不决定技术实质。先找作者给出的完整成功/失败 trajectory 或算法，画出：

**目标/可见信息 → 模型决定 → harness 执行工具 → 环境状态变化 → 观察回传 → 更新上下文/记忆 → 继续、停止或转交。**

对初学者，harness 可类比工作台和调度规则；先用一次查找/执行动作讲通，不一口气讲完 planner、memory、reflection、多 Agent 等全部名词。教学示意与原文实际系统分开。

区分 **agent harness/scaffold**（让模型调用工具和循环）与 **evaluation harness**（运行任务、重置环境、评分和统计）；它们可能由同一项目实现，但评价对象和职责不同。工作流预设步骤与模型动态选择行动也要分开，不为命名争论代替机制分析。

## 用最小系统描述替代模块堆砌

| 对象 | 需要时找出的信息 |
|---|---|
| 任务/环境 | 初始状态、可观察/隐藏信息、动作空间、成功条件 |
| 模型 | checkpoint/API 快照、角色、提示与可见历史 |
| 工具 | schema、权限、返回值、错误/超时、执行反馈 |
| 状态与记忆 | 什么保存在哪里，何时读写/压缩/丢弃，是否更新权重 |
| 控制 | 规划、路由、反思/验证、重试、停止、人工转交和预算 |
| 多 Agent | 谁与谁通信、共享状态、独立上下文、协调/选择成本 |

找到一处关键设计改变，解释它如何改变上述循环。缺停止策略或记忆更新细节就留空并说明影响，不按熟悉框架补齐。完整代码核对仅在读者需要且来源可用时做，不为理解自动部署环境。

## 分开任务、尝试、轨迹、结果与规则

- **task** 是问题；**trial** 是一次执行；**trajectory** 是可见过程；**outcome** 是最终环境状态；**grader** 是如何判定。Agent 说“完成了”不是环境已完成。
- 最终答案/测试通过，可能仍未覆盖必须确认、工具权限、状态约束或副作用。反过来，工具暂时故障也不自动证明规划算法错误。
- 按任务目的分别评价任务完成、规则遵守、资源使用与稳定性；不从单个总分推出“可靠自主”。只检查实际任务存在的规则，不虚构限制。
- 过程案例先选一成功一失败（若有），追踪最早出现证据偏离的环节；区分模型决定、工具执行、环境/基础设施和评分器问题，不只看作者展示的精彩案例。

## 成绩是模型与系统共同产生的

评价架构贡献时核对：任务集/分母、同一底座、工具与检索权限、提示/调参投入、尝试次数、预算、人工提示、测试时修补及基准版本。好结果可能证明一个组合系统有效；若要归因 planner/memory/多 Agent，需要有隔离这些因素的证据。

优先比较相关的简单强基线：同模型单 Agent、固定工作流、直接检索+生成、相同候选数的简单采样/筛选。简单不自动更好，复杂也不自动创新。多 Agent 比较尤其要计总模型调用和候选选择预算。

**可靠性与指标：**

- pass@k 常指 k 次中至少一次成功；pass^k 常指 k 次都成功；最终定义必须回原文核对。best-of-k 还需说明谁能判断正确并选择，不能把 oracle 成功率当实际交付率。
- 重复运行先明确实验单位，任务相关性与难度异质性；不能把全基准平均成功率直接乘方当经验连续成功率。单次案例不证明稳定。
- 同时报完整任务集和预先说明的有效子集；排除 API 错误、超时、不可解题或无效任务会改变估计目标。区分基础设施故障与 Agent 故障，做敏感性讨论，不擅自一律计失败或一律剔除。
- 检查 task/trial 之间环境重置、缓存、文件/git 历史、共享记忆、并发资源、CPU/RAM/时限、网络/API 状态。刻意研究跨任务记忆时保留其设定并与无记忆对照，不能机械要求清空一切。
- 成本包含候选生成、所有角色/子 Agent、工具、verifier、重试、失败尝试及调参的适当口径；区分每次尝试、每个任务与每次成功的成本，不只统计成功轨迹。

## 可复现与可迁移结论

阅读完成后应能说明：配置与信息边界是什么，成功如何验证，失败归因在哪一层，预算为何可比，以及哪些条件改变后尚不知是否有效。保存重要配置、原文锚点和未解决的归因；不要把某一模型+环境的结果写成所有 Agent 的规律。
